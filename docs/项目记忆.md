## stat 阶段关键约定（2026-09-28 审计修复）
- **`stat-stage` 的 `--delay 必须 >0`（门里用 2）**。根因：C# `RedisStat.AddDelayQueue` 会启动后台 `TransferAsync` 大循环（`TransferInterval` 默认 10s）把到期消息从 `{name}:Delay`（zset，db+1）ZREM 后 LPUSH 进主队列；demo 进程暂存后立刻退出，若消息在存活期内到期（delay=0），后台线程可能被杀在 ZREM→LPUSH 之间 → **消息永久丢失**（实测 6 轮丢 2 轮；指纹=`moved=0` 且延迟 zset 与主队列皆空）。delay>0 时消息在生产进程存活期内不到期，转移只发生在消费侧，确定。
- 消费端必须能处理「消息还在延迟 zset」的输入：
  - Rust `stat-process-once`：循环 `transfer_due_once` + `consume_once`（已有）
  - C# `stat-process-once`：显式驱动 `RedisDelayQueue.Take` → 主队列 `Add` 循环（2026-09-28 新增；不要依赖 TransferInterval 节拍）
- 双向已验证：A=Rust stage→C# process、B=C# stage→Rust process；修复后双向各 3 轮 + 全门通过。

## 其他坑（会话实录）
- mock 对空集合（如 zset）不清键 → `exists` 探针可能误报「键存在」，别据此判断消息在不在。
- `clean`（双侧）只清 `{prefix}*` 的主库（db0）；stat 的队列键在 db1，靠协议流程自清理。
- `stat-process-once` 里 C# 的消费大循环用 BRPOPLPUSH（timeout=rds.Timeout/1000-1），消息落主队列即被取走。
